## 4. KEDA SQS scaler IAM action

Source: `pkg/scalers/aws_sqs_queue_scaler.go` at tag `v2.21.1` (blob
`d312a09ead23735064708b54cd8f6f05764a34ac`). The scaler's client interface has one method,
`GetQueueAttributes` (lines 77–85), called once per poll (lines 180–185) for
`ApproximateNumberOfMessages`, plus `ApproximateNumberOfMessagesNotVisible` when `scaleOnInFlight`
is true (the default) and `ApproximateNumberOfMessagesDelayed` when `scaleOnDelayed` is true. There
is no `ListQueues`, `GetQueueUrl` or `ReceiveMessage`. `queueURL` can come from the trigger or a
resolved env var; `awsEndpoint` is optional (used by the kind lab).

Result: the KEDA operator role needs exactly `sqs:GetQueueAttributes` on the one queue, as P6-T3
already states. Closes SPEC §11 S3 ("exact IAM action").

## 5. KEDA 2.21 service-account token audience change

Source: `kedacore/keda-docs` `content/docs/2.21/migration.md`. 2.21 defaults to
`operator.serviceAccountTokens.mode: enforce-audience`. The page says this breaks Vault Kubernetes
auth and every `boundServiceAccountToken` TriggerAuthentication, and that the authentication
source, not the scaler, decides the impact.

P6 uses `ClusterTriggerAuthentication` `zdr-sqs` with `podIdentity.provider: aws` and the
operator's IRSA identity. IRSA uses the web identity token that the EKS Pod Identity webhook
projects for audience `sts.amazonaws.com`; it is neither Vault nor `boundServiceAccountToken`.
Result: **not affected**; no audience mapping is needed. Closes SPEC §11 S2. The operator
ServiceAccount still needs the IRSA role annotation (window step, like P4).
